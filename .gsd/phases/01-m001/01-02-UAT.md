# S02: End-to-end integration and acceptance verification — UAT

**Milestone:** M001
**Written:** 2026-07-22

## UAT Type

- UAT mode: mixed
- Why this mode is sufficient: The automated layer (unit tests) proves the seeding code path is exercised under a test harness. The manual layer covers the visual rendering that cannot be driven headlessly — panel population on reattach and Pause wind-down behavior require a running Electron + pi process.

## Preconditions

- gsd-tau built and running (dev: `pnpm dev` or packaged build)
- pi (gsd) installed on PATH, version ≥ 1.11.0
- An existing GSD project on disk (with at least one milestone in `.gsd/gsd.db`)
- A second project that has *no* GSD state (to test empty-panel case)

## Smoke Test

Open a GSD project that has existing milestone state; the auto-run panel should appear populated with the last known milestone/slice/task tree within ~1 second of the project loading — before any new prompt is sent.

## Test Cases

### 1. Initial open-time seeding

1. Launch gsd-tau
2. Open a project that has `.gsd/gsd.db` with at least one milestone
3. Navigate to the auto-run panel (or wait for it to appear)
4. **Expected:** Panel shows the milestone tree seeded from Path B (gsd_milestone_status reconciliation). No prompt was sent; pi did not start a new run.

### 2. Reattach seeding after tab close

1. Open a project; confirm panel is seeded (test case 1 passes)
2. Close the project tab
3. Re-open the same project
4. **Expected:** Panel is seeded again from Path B — it does not show a blank/loading state on the second open.

### 3. Live Path A + B during active auto-run

1. Open a GSD project
2. Send `/gsd auto` with a valid task
3. Observe the panel while pi is running
4. **Expected:** Panel updates live as pi calls workflow tools (Path A — tool_use events). Milestone/slice/task tree reflects in-progress state.

### 4. Pause winds down pi within 10 seconds

1. While `/gsd auto` is running (test case 3)
2. Click the Pause button
3. Start a stopwatch
4. **Expected:** pi sends abort() + /gsd stop, session returns to idle within 10 seconds. Panel reflects stopped/idle state.

### 5. New project shows empty panel

1. Open a project that has NO `.gsd/gsd.db` (fresh directory)
2. Navigate to the auto-run panel
3. **Expected:** Panel shows an appropriate empty state (no tree, no error). No crash or unhandled rejection logged.

## Edge Cases

### ENOENT resilience

1. Open a project where `.gsd/gsd.db` exists but `STATE.md` is missing
2. **Expected:** Panel seeds from the DB alone; no crash. (Covered by unit test T01/ENOENT case.)

### No-milestone skip

1. Open a project where `.gsd/gsd.db` exists but has no milestones
2. **Expected:** seeding completes silently; panel shows empty state. (Covered by unit test T01/no-milestone case.)

## Failure Signals

- Panel blank after project open (Path B seeding silently failed — check main-process log for `[handlers] reconcileProgress error`)
- Console unhandled rejection on open
- Pause takes > 10s to return session to idle
- Crash or white screen on open with fresh project

## Not Proven By This UAT

- Visual styling and layout of the auto-run panel
- Correct rendering of nested slice/task nodes
- Token cost / model picker / context gauge integration
- Multi-window or multi-tab session isolation

## Notes for Tester

The unit tests (T01/T02) already verify the seeding code path mechanically. Manual steps above fill in the visual layer. If test cases 1–2 fail, check `%APPDATA%\gsd-tau\logs\` for the main-process structured log — `[handlers] post-open Path B seeding` lines indicate whether the seeding call was made and whether it returned hasData=true.
